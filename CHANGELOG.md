Newest first. "Beta" means the skill was added under `skills/in-progress`.

- `3.11.1`: `adapt` (beta) is rebuilt around the stop: the human sees a message only when the agent ends its turn on it. On the skill's first real task, the owner reported that an agent running a command that waits for the owner's approval never said it was waiting. The agent found a cause, designed a change to the command, built it, and opened a pull request about 40 minutes after the request. The owner's only message in between asked why it was taking so long. The change reversed a decision the owner had recorded in an ADR eight days earlier, and that ADR lists the design the agent built among the alternatives the owner had rejected. The agent's notes say twice that reversing it was the owner's call. Its opening message filed the reversal under assumptions and said it was starting now. The owner never saw that message. The agent wrote it in the middle of a turn and kept working, and the owner's interface folds such text among the tool calls and shows the message the turn ends on. Asked afterwards why it had not waited, the agent quoted "Then start", "Each stands unless they object", and "Continue with the work that does not depend on the answer" from the skill, and its harness's general instruction to avoid stopping while work is owed. It also said the work was local and reversible until the pull request. It had weighed eight alternatives and written two in the opening message. It had reproduced the problem in its own harness and had not asked which agent the owner was using, though the ADR says a second agent shows a command's output while it runs. The skill told the agent to write for the human and keep working in four places: the opening message when nothing was the human's to decide, the assumptions that stood unless the human objected, the one-line notice when evidence changed the route, and the note that the agent did the work itself when it could not hand it over. None of those reaches the human. `adapt` now names two kinds of text. A message that ends a turn is written for the human and stands alone. Everything else is notes for the agent, and the contract and the route are notes. The agent stops before it builds when solutions differ in what someone uses or sees or in the mechanisms the project owns, when the solution changes something the human decided and recorded, when the problem or the solution rests on a fact only they hold, when the scope differs from the request, or when something is hard to undo or reaches other people unasked. That message gives the decisions, the problem beside what was checked and what is still assumed, the solution beside the others the agent weighed, and where the work lands. The skill says the stop holds over a general instruction to keep working, and that a reply about something else leaves the question open. When no decision is the human's, the agent writes them nothing and works, and it stops when in doubt. The details it chose for them go in the report, each with what changes if it is false, and a detail that would not be cheap to reverse there is a decision of theirs. The report carries the whole picture, because without an earlier stop the human has seen no plan. A turn that ends for another reason, such as a long command still running, ends on a message that stands alone too. The agent also establishes how the human met a reported problem, and counts a reproduction in a different setup as an assumption. Two agents that did not write the change each played an agent at the end of step 1 of the rebuilt text, one on the task above and one on a bug with a single fix. The first wrote notes and ended its turn on two questions. The second wrote nothing for the human, wrote its contract as notes, and started. Three sentences they found ambiguous were then rewritten, and nobody ran the text again after that. The new text has not run on a real task.

- `3.11.0`: Adds `adapt` (beta), a user-invoked skill that works one task through a process designed for that task. `strategic-programming` judges an existing pattern before repeating it, and `writing-for-people` (beta) puts the proof beside each claim and gains the diagram as a format. The catalog had grown from about 20,900 words at 2.0.0 to about 38,500, and this release adds about 1,900 more. The 2.0.0 commit says of its predecessor that each retro added rules. The same happened here, and each rule applies to every task. The agent that wrote this change read the owner's recent work, and nobody checked its figures by hand. In one delivery the production change was a tool that returns an empty list. It took 77 minutes from the request to a pull request with green checks and used 11 subagents. The same day the owner dictated a two-step process for a production bug, a diagnosis and then an independent attempt to refute it, and had a confirmed cause in about 20 minutes. `adapt` is tried beside `shape` and `deliver` and replaces neither. The agent reads first, questions the request, and weighs the stakes, which set how much process the task gets. It states the idea, what it assumed, a contract whose every line names a proof that fails when the line is false, and the route. Then it starts, and waits only for what is the human's. The work can go to an implementer the user names, such as a cheaper model. In one delivery run that way, the orchestrating agent reported that the cheaper model had every acceptance test passing in 28 minutes, and more than seven hours then passed across six review rounds before the pull request was ready. By the same reports, 30 of 100 deliberate changes to the code failed no test in the first round, and three reviews by a stronger model found defects after three rounds by the cheaper one. So in `adapt` the designer runs each proof itself, and the brief holds what will be verified and what the repository cannot tell. How much detail a brief needs is not known. The designer names each finding's cause as guessed, ignored, or misled, and reports the brief's size beside the change's, so that use can settle it. An agent that did not write `adapt` read it against three invented tasks, and its findings were fixed. Nothing was executed, and `adapt` has not run on a real task. `strategic-programming`'s list of options put reusing the repository's established pattern second, and the agent stops at the first option that works. 3.9.0 records an agent that planned around a column type nobody had chosen. Option 2 now reuses an implementation by calling or extending it. A pattern is judged before it is repeated. One with a reason is followed. One without competes with the simplest form, and the comparison counts the old sites, because a better form beside them is a second mechanism. The changes to `writing-for-people` come from a literature review that two agents ran for this change, with a third checking their sources. No person checked them, and most of the practices are inferences from studies of students and operators. In those studies, longer explanations raised confidence in an AI's answer without raising accuracy ([Steyvers 2025](https://doi.org/10.1038/s42256-024-00976-7)), explanations raised acceptance of right and wrong answers alike ([Kim 2025](https://doi.org/10.1145/3706598.3714020)), and making a check cost less than the task reduced overreliance ([Vasconcelos 2023](https://doi.org/10.1145/3579605)). Ego depletion did not hold in large multi-site replications ([Hagger 2016](https://doi.org/10.1177/1745691616652873), [Vohs 2021](https://doi.org/10.1177/0956797621989733)), so asking the human for fewer decisions rests on the cost of each interruption. The same review gives the sources for the rest: a person holds three to five new items at a time ([Cowan 2001](https://doi.org/10.1017/S0140525X01003922)), a recommended option is chosen more often ([Jachimowicz 2019](https://doi.org/10.1017/bpp.2018.43)), and a diagram helps when its labels sit inside it and the reader does not already know the structure ([Schroeder and Cenkci 2018](https://doi.org/10.1007/s10648-018-9435-9), [Tetzlaff 2025](https://doi.org/10.1016/j.learninstruc.2025.102142)). `writing-for-people` now opens a message with the task and where it stands for a reader who comes from other work, puts the proof beside each claim the reader will act on, has the writer say what was verified, assumed, and not checked, marks a recommendation as one with what would make it wrong, and uses a diagram for a structure the reader does not already know.

- `2.5.0`: adds `pr-description` (beta), which writes or rewrites a pull request's description for its reviewer, and takes that job out of `ship`. The rules `2.4.0` gave `ship` did not hold. The next delivery loaded `ship` and still published a description built from its own report. It had acceptance example IDs, a section on `refine`'s round, spike notes meant for the next piece of work, and a "program design departure", and it lacked the reading guide `ship` asked for. The owner had also opened pull requests outside `deliver` and wanted the same guidelines there. A research run (two independent researchers and a judge) set the structure. Why the change exists is the reviewer's best-supported need: Tao et al. 2012, Bacchelli and Bird 2013, Ram et al. 2018, and the Google, Git, and Linux guides all name it. Agent pull requests whose description was highly inconsistent with the code were accepted 28% of the time against 80% for the rest, and the most common inconsistency was claiming changes the diff lacked (Gong et al. 2026, observational). When people edited Copilot's descriptions, they added intent, test information, and visuals, and cut file-by-file walkthroughs (Xiao et al. 2024). Length mostly tracks how complex the change is. The research found no study that measures what narrating the workflow costs, so leaving it out rests on the Git, Linux, and Google guides. The skill orders the description as why, what changes, decisions, how to review (only for large or multi-area changes), what was tested, including what was not, and what is left out. It works from the final diff instead of the notes of the work. A table maps each kind of process material to a statement about the code or to its own home. Each fact it may state goes on a claims list with its source: the diff, a run, a person who said it, a document, or the agent's own inference, and a claim taken from an earlier run, the change's own documents, or an agent's report counts only as a lead. Before publishing, a fresh agent that saw none of the work traces every claim to its source, marks it supported, attributed, inference, or unsupported, flags every name, link, or detail the repository's visibility should not reveal, and reads the description cold as the reviewer. On its first use, rewriting that delivery's description, the cold reader found a claim copied from the change's own ADR that the diff contradicted. - `2.3.0`: adds `editor` (beta), the catalog's first skill for prose rather than code. The owner wanted an editor for the articles and essays they write in Spanish and English: one that takes a piece from the idea to the final version without writing it, reads as several readers to find holes, and helps them improve across pieces. The design rests on a research run (two independent researchers and a judge) and on eight choices the owner made where the evidence left one open. Writers cannot see their own holes because they know what they meant, and watching real readers react is what teaches them to anticipate one (Traxler and Gernsbacher 1992; Kellogg 2008), so each reader is a separate agent that reads the draft cold and reports what happened to it, and the editor adds the diagnosis. Its reports count as clues, since the evidence that a model can simulate distinct readers is thin. The editor works from structure down to surface, as professional editing standards and Cassany's _Reparar la escritura_ order it, and raises few, located issues per round. It never contributes claims, arguments, or passages: model-written text makes different writers converge, lowers their sense of authorship, and can shift their views, and unguarded AI help improves the draft while hurting later learning (Doshi and Hauser 2024; Draxler et al. 2024; Jakesch et al. 2023; Bastani et al. 2025). It marks a problem with its place, kind, and a hint, and gives the correct form of the writer's own sentence only after they tried, which matches the evidence on written corrective feedback for second-language writers.
