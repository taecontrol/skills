# Changelog

Newest first. "Beta" means the skill was added under `skills/in-progress`.

- `3.1.0`: adds `writing-for-people` (beta), which decides what a person needs from a text before it is written. A review of the owner's T3 Code threads on three machines, from August 24 to November 4, found about 194 corrections to how agents wrote for people. Most were about content, not wording. About 50 were "no entiendo" at a term, code, or ID nobody explained, such as an acceptance example number or a question number. About 30 were messages that did not answer the owner's question, left out the URL or the step's location, or asked about a design the owner had never seen. About 25 were noise, such as lines that repeat a chart or notes about who reads the page. About 20 were decisions without a reason, and 16 were internal process, such as spec IDs and workflow steps, in tickets, wiki pages, and pull requests. `unslop` only fixes wording, so these came back even when it ran: one design thread drew about 38 corrections in two weeks, and one wiki page needed four fixes in an hour. The owner typed `$unslop` by name about 25 times and `$wait-what` about 16 times. The re-pitches that worked shared one shape: the decision first, an example from the owner's own data, two or three options with plain consequences, and a recommendation. `writing-for-people` makes that shape the first draft. It explains each term where it appears, because a separate context tab did not help. It takes `pr-description`'s process material table for every text others read, and it ends with a cold read by a fresh agent before the text is published. `wait-what` keeps its triggers and rewrites through it. `shape`, `deliver`, `grilling`, and `walkthrough` write through it in place of `wait-what` and `unslop`. The skill sets no reply language: in 14 corrections an agent running `shape` had taken an English issue title as the owner's language, and the owner's own agent instructions now name the language. `unslop` rule 16 now also catches one label repeated on every item, such as "Why this example:", which the owner called AI slop.
- `3.0.1`: a shape found most of its gaps only because the owner asked for checks the workflow did not run. The spec fixed a bug in how an AI client writes JSON stores to an outside platform, and its program design changed how an approval page shows each change. When the spec was ready to accept, the owner asked for a fresh review. It found 15 problems, and 2 were blockers. In one, an example assumed that an existing merge function merged nested objects. The agent had judged that from the function's name, but the function replaces them, as its comment, its tests, and the documentation said. Two more reviews and a second spike, also asked for by the owner, found 4 more gaps, such as the size and cost of the stored diff. They also found three behaviors the design relied on that nobody had observed: the platform simplifies the permissions it stores, the database column reorders JSON keys, and the merge reorders keys too. Delivery then found that the platform's validation errors arrive in a field the code never reads. Nearly every gap was a behavior of something the change leaves untouched. Each one appeared while the agent wrote the examples and the program design, after `shape`'s step that requires observed facts had closed. Running the real merge function and the real platform took minutes each time. `program-design` now has the agent run each behavior a call path relies on outside the change, as `architect` already does for platform behavior. `shape` gains a step before acceptance. A fresh reviewer gets the spec, the program design, and the code, but not the agent's reasoning. It looks for examples the code contradicts, missing states, behavior nobody observed, and existing tests or callers the change breaks. It reviews what the fixes touched again, until a round finds no blocker. The walkthrough page's reviewer still checks the page against the spec, and this reviewer checks the spec against the code.
- `3.0.0`: promotes `bug-hunt`, `program-design`, and `walkthrough` to stable, removes `how`, `why`, and `domain-language`, and makes `wait-what` reachable by agents. The decisions come from a month of T3 Code threads on the owner's two machines. In that month `program-design` was used 40 times across 34 conversations and `walkthrough` 35 times across 34, and `bug-hunt` 40 times across 9, so the three move from `skills/in-progress` to `skills/engineering`; `editor` and `pr-description` stay in beta. No agent and no person loaded `how` or `why` in that month. The owner suspected the descriptions, since they often ask "¿por qué?" or "¿cómo funciona?", so a review read the roughly 45 questions of that kind on one machine, with a sample from the other. Most pushed back on the agent's own proposal, asked about an outside product, or said the last message had not landed, and a trigger on "por qué" would likely have fired on those by mistake. Of the roughly 12 real questions about why code is the way it is or how it works, 11 got a grounded answer on the first try without either skill. `prune` and `bug-hunt` told their agents to use `why`, and it never loaded; they now carry the one step from it they needed: trace a strange shape through the commits, pull requests, and issues that introduced it, and treat any reason no source from that time records as a guess. Neither skill is replaced. `domain-language` loaded 57 times, every time in a subagent; the review traced those loads to `deliver` and to the skill's broad description. Of the threads the review read on one machine, 23 showed no effect, 5 made glossary edits that the parent's prompt already spelled out, and 2 changed a glossary entry on their own. In projects without a glossary, the review found no corrections about naming from the owner. `deliver` now says it directly: a new or changed domain term goes into the project's glossary in its existing format, and a project without one gets one only when the human agrees. `wait-what` was used 7 times, 6 of them typed by the owner, while the review counted about 23 times on one machine alone that the owner said they did not follow; its description named no condition an agent could act on. It now names them in English and Spanish: the user does not follow a message or one item of it, asks again what to decide, or asks for their language. Its body leads with what the user must decide, replaces or defines every label they have not used, and keeps their register, after the review found one re-pitch that switched to "usted". The review also found that the confusing messages came first from how agents write: a buried bottom line, labels like example IDs and type names, another agent's report passed on in its own vocabulary, and English replies to Spanish messages, 34 of the 953 agent replies to a Spanish message on that machine. So `wait-what` now carries a rule against each of these and also runs before an agent passes another agent's report to the user, and `shape`, `grilling`, and `deliver` write their questions, stops, and reports the way it writes a re-pitch.
- `2.5.0`: adds `pr-description` (beta), which writes or rewrites a pull request's description for its reviewer, and takes that job out of `ship`. The rules `2.4.0` gave `ship` did not hold. The next delivery loaded `ship` and still published a description built from its own report. It had acceptance example IDs, a section on `refine`'s round, spike notes meant for the next piece of work, and a "program design departure", and it lacked the reading guide `ship` asked for. The owner had also opened pull requests outside `deliver` and wanted the same guidelines there. A research run (two independent researchers and a judge) set the structure. Why the change exists is the reviewer's best-supported need: Tao et al. 2012, Bacchelli and Bird 2013, Ram et al. 2018, and the Google, Git, and Linux guides all name it. Agent pull requests whose description was highly inconsistent with the code were accepted 28% of the time against 80% for the rest, and the most common inconsistency was claiming changes the diff lacked (Gong et al. 2026, observational). When people edited Copilot's descriptions, they added intent, test information, and visuals, and cut file-by-file walkthroughs (Xiao et al. 2024). Length mostly tracks how complex the change is. The research found no study that measures what narrating the workflow costs, so leaving it out rests on the Git, Linux, and Google guides. The skill orders the description as why, what changes, decisions, how to review (only for large or multi-area changes), what was tested, including what was not, and what is left out. It works from the final diff instead of the notes of the work. A table maps each kind of process material to a statement about the code or to its own home. Each fact it may state goes on a claims list with its source: the diff, a run, a person who said it, a document, or the agent's own inference, and a claim taken from an earlier run, the change's own documents, or an agent's report counts only as a lead. Before publishing, a fresh agent that saw none of the work traces every claim to its source, marks it supported, attributed, inference, or unsupported, flags every name, link, or detail the repository's visibility should not reveal, and reads the description cold as the reviewer. On its first use, rewriting that delivery's description, the cold reader found a claim copied from the change's own ADR that the diff contradicted. Then the description of the pull request that added the skill linked a private repository from this public one, which is why the check covers exposure too. `ship` opens the pull request with it, and `deliver` gives its report to the human in its final message rather than in the pull request.
- `2.4.0`: a feature delivered for a team showed three places where the workflow served its owner and not the people around them. Shaped as one spec, the feature became one pull request of more than 600 files, so the team saw nothing until it was done and could not review it whole. `shape` now splits work that does not fit one pull request a reviewer can read whole into slices, each with its own issue and pull request. When the project names where its team keeps plans, `shape` also writes a plan there for people, opened as a draft once the split is agreed. The plan holds the problem, the behavior in plain words, each decision with its reason, the slices, and what is still open. Research, spikes, and prototypes become sections of the plan instead of issues. Each project records its tracker, where plans live, and the language of shared work through `agents-md`, so the workflow names no tool, and a project that records none works as before. The same pull request had a description of about 4,300 words written for the person who shaped it, full of spec example IDs, review rounds, and departures from a spec the reviewers could not open. `ship` now writes the description for the reviewer, with what the change does and why, how to review it, how to try it, the decisions worth knowing, and what it leaves out, and runs `unslop` on it. `deliver` gives the process details to the owner in a report instead. Last, after `refine` finished its three rounds, the project's own pre-merge review found 66 blockers in four runs. Of the first 20, `refine`'s rules had demoted 10, four of which it had found itself. Another 4 were outside its lenses, and it missed 6. `refine` now blocks on a confirmed defect in any code the change modifies or newly reaches, even when the spec says nothing about it, and on a mutation that survives on a security guard. It splits a large review by lens across the whole change instead of by area, and adds two lenses. One reads how the product runs from its deployment configuration, such as replicas, other entry points, and the previous release during a rollout. The other reads every changed sentence of documentation against the code. A fresh agent confirms or refutes each finding before it is sorted. Later rounds review the whole change, because about 28 of the 66 blockers came from code an earlier fix added, and a fix that needs a mechanism the spec never asked for goes to the owner as a scope decision. `refine` keeps its three-round limit and blocks only on serious harm, since the project review never converged and blocked on low-severity findings.
- `2.3.0`: adds `editor` (beta), the catalog's first skill for prose rather than code. The owner wanted an editor for the articles and essays they write in Spanish and English: one that takes a piece from the idea to the final version without writing it, reads as several readers to find holes, and helps them improve across pieces. The design rests on a research run (two independent researchers and a judge) and on eight choices the owner made where the evidence left one open. Writers cannot see their own holes because they know what they meant, and watching real readers react is what teaches them to anticipate one (Traxler and Gernsbacher 1992; Kellogg 2008), so each reader is a separate agent that reads the draft cold and reports what happened to it, and the editor adds the diagnosis. Its reports count as clues, since the evidence that a model can simulate distinct readers is thin. The editor works from structure down to surface, as professional editing standards and Cassany's _Reparar la escritura_ order it, and raises few, located issues per round. It never contributes claims, arguments, or passages: model-written text makes different writers converge, lowers their sense of authorship, and can shift their views, and unguarded AI help improves the draft while hurting later learning (Doshi and Hauser 2024; Draxler et al. 2024; Jakesch et al. 2023; Bastani et al. 2025). It marks a problem with its place, kind, and a hint, and gives the correct form of the writer's own sentence only after they tried, which matches the evidence on written corrective feedback for second-language writers. A notebook kept by language records the writer's recurring patterns, has them find each one before the editor points to it, and stops hunting a pattern once they find it first in two pieces in a row.
- `2.2.0`: adds two beta skills from a five-day shape whose owner accepted an architecture that was not yet clear to them, got its diagram on day four after accepting it on day two, and spent five rounds correcting the form of documents for humans. `walkthrough` renders a design as a self-contained visual page from its Markdown sources, filling a shared HTML template instead of redesigning the page each time: chapters that each answer one question with one visual, examples, decisions, and terms in their own tabs with inline popovers, diagrams on pannable canvases, one step-through per flow, a neutral palette, and zero layout shift. The Markdown stays the single source of truth that agents read; a fresh reviewer checks every fact and diagram on the page against it after each change, since text and diagram had drifted after an edit. `program-design` settles the shape of the code inside the components before agents write it: where each thing lives, the key types and the mistakes they refuse, the important call paths in production and tests, what each module hides, and how errors travel, grounded in the code and agreed one decision at a time. `shape` runs `program-design` when its gate lets the change in and has the human accept on the `walkthrough` page; `architect` presents its package through one; `deliver` follows an accepted program design and names each departure in the pull request; `refine` checks the diff against it.
- `2.1.3`: a shape fixed the numbers its checks impose without an outcome to derive them from. An issue that left "repeated enough times" and "sample count chosen by evidence" open came back with round numbers: 100 determinism runs that never reached the owner as a question and took over 30 minutes of full CPU, 10 full local runs accepted with an "ok" that took about 45 minutes and were later defended as contract, and mutation checks priced at "a few seconds per patch" that took 81% of the CI job and found nothing. `shape` now agrees on the outcome with the human before anything derives from it, counting the owner and their agents as the ones who have the problem when the change is verification or tooling. Every number a check imposes that costs run time or confidence, and every check added to CI, states the outcome it protects, its evidence, its measured cost locally and in CI, and the cost of getting it wrong; a number the evidence does not settle goes to the human with what each value costs and buys. `grilling` asks in plain words, with what each option buys and costs and why it recommends one, since the owner accepted questions full of jargon before understanding them. `deliver` treats a number that sets how much to verify as a decision, not as the contract, times one run before a long or repeated verification, and gets a fresh review for production changes made after `refine`. The same run lost a spec, a brief, and an inventory with their worktree, and rebuilt 37 examples from tests because a later issue depended on another issue's local spec: `shape` now publishes what later work needs to the issue or durable documentation, and anything that outlives the worktree cites only what outlives it too.
- `2.1.2`: a shape deferred a fact it could observe. `architect` presented a design with "verify the platform's constraint errors at implementation", and `shape` carried it into the spec as a known risk that would send the work back to design if it failed. A spike run only after the owner asked for it changed the accepted design: two constraints instead of one, and a new rule for detecting retries. `architect` now spikes every platform behavior its package relies on before presenting it, and keeps as open risks only what no observation within the bound can settle and no answer would reopen. `shape` is done only when every fact the spec depends on is observed: a risk whose failure would reopen design is an open question, and a spike settles it. A rabbit hole that could reopen a decision is an open question too.
- `2.1.1`: `bug-hunt` (beta) follows the evidence of its first run. Invoked without an area, it hunts the whole project in lanes along owner boundaries instead of picking one area, which had confirmed nothing where the whole project held eight bugs. It fixes every easy cause unless the user sets a limit, instead of at most three, so easy bugs no longer become issues. Every fix lands in one draft pull request with each cause in its own commits, as in `garden`, and the full gates run once on that branch. An unclaimed open issue for an easy cause is fixed and closed by the pull request instead of left alone.
- `2.1.0`: promotes the delivery workflow to stable: `shape`, `deliver`, `refine`, `ship`, `garden`, `prune`, and `setup-verification` move from `skills/in-progress` to `skills/engineering`. Adds `bug-hunt` (beta), a user-invoked hunt for bugs nobody has reported. It reads one area as a skeptic, keeps only the bugs a reproduction turns red, and groups them by cause. Each easy cause, local to one owner, settled by the code's own contract, and free of one-way doors, becomes a draft pull request with its regression test committed before the fix; the rest become issues an agent could pick up, or comments on the issues and pull requests that already cover them. It runs to the end without asking, so it can run from a scheduled task. `garden` and `prune`, which mostly run that way too, now finish on their own as well. `garden` picks the causes worth their cost instead of waiting for the human, fixes them in one pull request with each cause in its own commits, runs `prune` on its own worktree when the tests lens leads or the user asks and brings its commits onto the branch, and files every other cause after checking for an existing issue, marking apparent defects as suspected bugs for `bug-hunt`. `prune` can now be invoked by other skills, ships its own pull request when run alone, and hands its commits to the calling skill otherwise. Issues and pull requests from `garden` and `bug-hunt` carry their skill's label, so the next run can prefer an area the last ones did not cover.
- `2.0.4`: closes the gap where costly-to-reverse decisions went unowned. `shape` now settles every **one-way door** the change would make: persisted data or its schema, a contract that writes, a security boundary, or a seam an accepted ADR governs. It sizes each for the open issues that will share it and runs `architect` on each, whose gate, not the agent's own sense of reversibility, decides when no design is needed. Its state space for a write covers a lost response and its retry, every order of concurrent writers, and the data, queued work, and previous version that exist when the change lands; its real target is always isolated from the owner's own data, credentials, and session. `deliver` stops on a one-way door the spec does not settle instead of deciding it. `architect` is invoked when shaping or delivering meets a one-way door, checks a retry that meets a different outcome than the first attempt, and keeps a brief that constrains later issues where they can reach it. `adr` writes new records as `Accepted`, since merging is acceptance. `prototype` stops what it started, and `ship` files a failure that also happens on the base so the next delivery inherits the diagnosis.
