# Creation and maintenance workflow

Use the same workflow to create a package and to reconcile an existing one.

1. Inventory product-owned surfaces, user entry points, routes, registered
   commands, flags, public APIs, stable handles, persistent effects, current
   automation, launch ownership, and available second observation seams.
2. Compare that inventory with canonical CLI `--help`, the operating guide, and
   every Feature Map entry. Classify each item as `confirmed`, `changed`, `missing`,
   `unreachable`, or `obsolete`, with direct product or repository evidence.
3. Return material product-contract contradictions or costly architecture gaps to
   the Coordinator. Repair local control and documentation gaps within the
   accepted behavior. Do not invent speculative features or copy internal-only
   behavior into the map.
4. Update one coherent feature batch across CLI, guide, Feature Map, evidence
   schema, and focused tests. A user-facing behavior change updates its map and
   required control capability in the same candidate, or records an explicit,
   evidence-backed `no map impact` disposition.
5. Run representative recipes against the exact candidate. Exercise failures as
   well as success, retain direct artifacts, and confirm one persistent effect
   through an independent read-only seam.
6. Remove an obsolete entry only when product evidence demonstrates removal.
   Keep unreachable and unsupported paths explicit with the exact missing
   capability. Report remaining uncertainty rather than filling gaps by inference.
7. Recompute candidate, adapter, Feature Map, build, fixture, and relevant
   environment identities. Prior evidence is stale when any judgment-relevant
   identity changes.

Completion: the inventory classification is exhausted for the selected batch,
help/guide/map agree, recipes execute from a fresh context, control-plane tests can
expose stale identity and unsafe ownership, and uncertainty remains visible.
