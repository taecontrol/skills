## Description

Agents create products from abbreviated receipt names, so the catalog fills with duplicates and unclear names such as `GALLO`. Nothing can list or edit products today. A product whose only purchase was deleted can no longer be found by `find_products`, so recording that receipt again creates a duplicate. Price comparison (#9), the shopping list (#10) and restock rhythm (#11) also need a **kind** ("arroz", "leche") that groups brands and presentations. This PR adds catalog tidying over MCP and HTTP. The screens #8 asks for moved to #16, so this closes #8 without them.

## What changes

- **Nine new operations**, served from the operation registry over HTTP and both supported MCP protocol versions (2025-06-18 and 2026-07-28):
  - `list_products` lists current products, including ones with no purchases, with how many purchases (receipts, not lines) include each product, last purchase date and the active merges into each. It can search name and brand (merged names included), filter by `kind`, `withoutKind` or `withoutPurchases`, and resolve a merged `productId` to its current product. A cursor pages it (default 20, max 50).
  - `update_product` edits name, brand, size and kind; `null` clears brand, size or kind.
  - `merge_products` (with a `requestId`) and `undo_product_merge`.
  - `delete_product` deletes only a product with no purchases. Every product merged into it goes with it (a merged-away product never holds lines), along with every merge record, active or undone, that names any of them.
  - `list_kinds`, `rename_kind`, `merge_kinds` (no undo) and `delete_kind` (only when no current product has the kind).
- **Kinds are created by name.** A name that does not exist creates the kind; "Arroz" and "arroz" are the same kind. `record_purchase` and `correct_purchase` accept an optional `newProduct.kind`. In `record_purchase` it is ignored when evidence links the line to an existing product, as `newProduct` already is; in `correct_purchase` a `newProduct` always creates the product, so its kind is always applied.
- **`Product` gains `kind: { id, name } | null`** in every output that carries one: `get_purchase`, `record_purchase`, `correct_purchase`, `find_products` and the new catalog outputs. Inputs only gain optional fields.
- **Merging A into B** moves A's purchase lines to B. B keeps its name, brand, size and kind, and takes A's kind only if it has none. A's id still works for reads, linking and explicit picks, and leads to B. Who merged and when is recorded. Merging two products whose sizes are both known and differ is refused (`SizesDiffer`). Catalog writes through a merged-away id (`update_product`, `delete_product`, either side of `merge_products`) are refused with `ProductAlreadyMerged`, which names the target, who merged and when.
- **Undo returns A's purchase lines as if the merge had never happened.** A gets back its lines from before the merge, plus every line recorded or corrected later through A's evidence or an explicit pick of A's id, including through merge chains. Lines linked through B's evidence, or through evidence both products shared, stay on B. A returns with its own name, brand, size and kind; if its kind was merged into another meanwhile it gets the surviving kind, and if it was deleted, no kind. Edits made to B stay on B, including a kind B took from A.
- **Migration `0002_catalog.sql`** adds the `kinds` and `product_merges` tables, three nullable columns (`products.kind_id`, `products.merged_into`, `purchase_lines.via_product_id`) and indexes. It is expand-only. The previous Worker names its columns in every INSERT and SELECT, so it keeps working while the deploy applies the migration before the new Worker; its rows read as "no kind, not merged". Accepted residual: a merge issued within seconds of the swap, while the old Worker is still recording a line to the merged product, leaves that line on the merged-away product, where it reads as that product until the merge is undone. In the same window, an old-Worker correction of a line the merge already moved drops that line's origin, so a later undo leaves it on the target. While such a stray line sits on a merged-away product, `delete_product` of the merge's target fails with a generic database failure; no data is lost.
- Merging deploys the Worker and applies the migration. No screens: those are #16.

## Decisions

- **A merge moves lines; it does not resolve on read.** Every purchase line points at a current product (one that is not merged away), so `get_purchase`, `find_products` and the later price, list and rhythm queries need no merge logic. Undo works because each line keeps its **origin**, the product whose evidence (barcode, store code, receipt text) or explicit pick by id linked it, in `via_product_id` when that product is merged away. It never reaches the wire. [ADR-0010](https://github.com/taecontrol/despensa/blob/c47ef6a208f2212eae5d95aebb12a9501b521b96/docs/adrs/0010-merges-move-purchase-lines-and-keep-per-line-provenance-for-undo.md) records why, and the alternatives set aside: resolving merges in every reader, a per-merge list of moved lines, and a database trigger.
- **One line writer.** `insertLines` stores the origin's *current* product inside the INSERT, in the same batch as the purchase or correction, so a merge landing between a read and the write still leaves no line on a merged product. Undo depends on every line going through it.
- **Corrections keep a line's origin only when the caller keeps the product.** That means sending the line's current product id or its origin. Any other id, including a different merged-away id that leads to the same current product, is an explicit pick and becomes the line's new origin (`linkedBy: "chosen"`).
- **Guards run inside each batch**, not only in pre-checks: the merge record's `into_id` is a subquery that is NULL when either product is merged, missing, the same, or of a differing known size, so a concurrent change rolls the batch back. After a failure (pre-check or batch) the handler rereads in a fixed order: request id → `already_applied`, then source, target, sizes, else the original failure. So when two calls with the same `requestId` race, the loser returns `already_applied` with the winner's merge.
- **Retries:** a `requestId` already used returns `already_applied` with the stored merge, even if it was undone since. It never merges again. A reused `requestId` for a different pair is `InvalidInput`. Repeating an undo returns `already_undone`, and leaves alone a later merge of the same pair.
- **Edits are last-writer-wins, with no history**, and kind merges cannot be undone; a kind merge frees the old name, so classifying under it later creates the kind again. Tool descriptions say this.
- The full design (schema, batch SQL, the rule for which product links a line, and a table of concurrent situations) is in [docs/design/catalog.md](https://github.com/taecontrol/despensa/blob/c47ef6a208f2212eae5d95aebb12a9501b521b96/docs/design/catalog.md). `docs/design/recording-purchases.md`'s #8 note now points there.

## What was tested

`tests/catalog.test.ts` drives every scenario over HTTP and both MCP protocol versions against the Worker's own fetch handler with a real local D1 and the real Coto and Farmcity receipts in `tests/receipts.ts`. It covers:

- editing and listing, cursor paging, kinds by name;
- recording with a kind, including evidence that links an existing product and ignores the suggested kind;
- orphans left by `delete_purchase` and their deletion;
- the duplicate created by deleting a purchase and recording its receipt again, then merged;
- undo after later recordings through evidence and explicit picks, after a correction, across chains, and when the source's kind was merged or deleted meanwhile;
- refusals (differing sizes, merged ids, self-merge) with nothing written;
- retries, and two requests with the same `requestId` sent at once (`Promise.all`), whichever wins;
- line counts and totals unchanged across merge and undo;
- the migration over rows written with the previous Worker's column list.

`tests/mcp.test.ts` checks the nine tools and their hints on both protocol versions.

- `vp check` on the final commit: formatting, lint and types pass.
- Locally, `vp test run --maxWorkers=1` (one worker, as CI runs with two cores): 9 files, 150 tests pass. CI's `verify` runs the full `vp run verify`.
- `vite.config.ts` sets `fsModuleCache: false` for tests. With the cache on, Vitest sends each later test file one reply holding its whole transformed import graph, and the Cloudflare pool inlines every module into a single WebSocket message. With the catalog code, the Worker's graph reached 33.7 MB, above workerd's 32 MiB limit, so workerd closed the socket (1009) and every test file after the first crashed in CI. With the cache off, each module travels in its own message (the largest is about 1.5 MB). No test or check changed. `@cloudflare/vitest-plugin` 1.4.12 and 1.5.0 build the reply the same way, so upgrading does not fix it.
- Not covered by a test: a write from another call landing at a chosen point between one handler's read and its batch (for example, a merge between a correction's read and its write). The in-batch guards and `insertLines`' in-statement resolution cover them by construction; forcing those interleavings would need test-only hooks in production code.
