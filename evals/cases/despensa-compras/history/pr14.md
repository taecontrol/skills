## Description

The household comes back from the supermarket with paper receipts and wants Despensa to hold what they bought without typing it in. Until now Despensa had no data model and only `get_status`. With this PR an agent that has read the receipt photos records the whole purchase in one MCP call and reads it back. Correcting, deleting and listing purchases come next, in #13.

## What changes

- **Four new operations**, served over `POST /api/<name>` and as MCP tools, as every operation is (ADR-0004):
  - `list_stores` (read): the known chains and branches.
  - `find_products` (read): for each receipt line's codes or text, the product Despensa already knows, or the candidates when the evidence matches several products.
  - `record_purchase` (idempotent write): store, date, receipt identity, every printed line with its raw text, codes, quantity, unit price, amount and adjustments, receipt-wide adjustments, and the printed subtotal, discounts and total. It returns `recorded` or `already_recorded` with the stored purchase.
  - `get_purchase` (read): the purchase as stored, including who recorded it and how each line got its product (`linkedBy`).
- **Totals are checked, not computed.** Lines and adjustments must add up to each printed figure, or the call fails with `TotalsMismatch`, naming the check (`subtotal`, `discounts` or `total`) and the difference. Nothing is written.
- **Retries and repeated receipts return the original.** A retry with the same `requestId` returns `already_recorded` with the original purchase and leaves it unchanged. So does the same receipt sent under a new `requestId`, when it carries the complete fiscal identity: CUIT, point of sale and number. The CUIT is compared by its digits and the other two without leading zeros. A receipt missing any of the three is deduplicated by `requestId` only. For valid input, this lookup runs before the totals check.
- **Products are linked automatically only by exact evidence.** A line links to a known product by a valid barcode outside GS1's in-store prefixes (in any chain), by the store's article code (same chain), or, on lines with no codes, by the same normalized receipt text (same chain). An agent may also pick a `productId` itself; it is stored as `linkedBy: "chosen"` unless the evidence names the same product. A pick that contradicts a unique code match fails with `ProductMismatch`. Barcodes with GS1's restricted in-store prefixes 20–29 (on this Coto receipt: weighed items, empanadas, and packaged lines such as Coto's own lentils), all-zero barcodes and wrong check digits never link.
- **Who recorded it** comes from the verified Access email. The local build without Access settings records `local@despensa.localhost`.
- **Schema:** `migrations/0001_purchases.sql` adds the tables chains, stores, products, purchases, purchase_lines, purchase_adjustments and purchase_corrections. The deploy job applies it before deploying the Worker. It only adds tables and touches nothing the current Worker reads, so the Worker in production keeps answering `get_status` while the migration runs. A test checks `get_status` with the schema applied.
- **Access, already changed in the dashboard:** Managed OAuth now also accepts client registration from the Claude app's and ChatGPT's connector callbacks (ADR-0007). `docs/deployment.md` lists the callbacks and how to add Despensa as a custom connector in each app.

Merging deploys: the migration runs, then the new Worker.

## Decisions

- **Handlers get the signed-in member and D1 batches (ADR-0006).** The Access gate now returns the member it verified (`admit` in `src/worker/access.ts`), and `index.ts` provides `Member` and `D1Client` per request. A handler cannot take the recorder from its input. D1 has no interactive transactions, so a purchase is written in one `D1Client.batch`.
- **Whole purchases, two deduplication keys, exact evidence only (ADR-0008).** No drafts or partial state. `request_id` and `receipt_key` are both `UNIQUE`. When a concurrent write wins, the batch fails and the call rereads by both keys instead of parsing error text: `@effect/sql-d1` wraps every D1 batch failure as the same `UnknownError`, and D1 names the cause only in its message, so telling a constraint from an outage would rest on wording. No name similarity matching: a false link would silently mix two products' price history.
- **The data model and the agent contract are in `docs/design/recording-purchases.md`.** Later issues (#7–#12) build on it. During implementation its schema gained one column, `purchase_lines.linked_by`. The contract returns `linkedBy`, and deriving it at read time would change once later purchases add products. Review also changed the contract there: receipt identities may be partial, and totals outside the exact money range are refused before deduplication.
- **Money is exact.** The wire carries ARS as a JSON number with at most 2 decimals, decoded from its shortest decimal string to integer cents, never multiplied as a float. Sums use `BigInt`: adding floating-point cents once accepted a total of 0.02 where lines and adjustments added up to 0.03, because a huge line amount and a receipt-wide adjustment cancelled out. Computed totals outside the exact money range are refused as `InvalidInput`, during input validation and so before the duplicate lookup.
- **Inserts bind JSON arrays and read them with `json_each`.** D1 allows at most 100 bound parameters per statement, and a 27-line receipt has hundreds of values.
- **Flat optional fields instead of unions.** A line carries `productId` or `newProduct`, exactly one, as two optional fields, because remote MCP clients render `anyOf` unevenly. `tests/purchase-wire.test.ts` keeps the advertised schema flat and numeric.
- **Store article codes are assumed to be chain-wide.** If a chain turns out to reuse a code for different products across branches, store-code links can be wrong. Only receipts from several branches can show it.

## How to review

1. `docs/adrs/0006`–`0008`, then `docs/design/recording-purchases.md` (Caller usage, Schema, Shape and invariant owners).
2. `src/operations/purchases/`: the contract. `wire.ts` holds the shared schemas and money decoding, `totals.ts` the totals check, and one file per operation holds the description the agent reads.
3. `src/worker/purchases/record.ts`: the order of checks, the batch, and recovery after a failed batch. This is where the risk sits.
4. `src/worker/purchases/catalog.ts` and `codes.ts`: linking and normalization (GTIN check digit and restricted prefixes, store-code padding, text and receipt keys).
5. `src/worker/access.ts`, `index.ts`, `operation-layer.ts`, `member.ts`: the service seam.
6. Tests: `tests/purchases.test.ts` drives the two real receipts over MCP, alternating between the two protocol revisions (2026-07-28 and 2025-06-18), and reads purchases back over HTTP where the example calls for it. `tests/receipts.ts` is their transcription and can be skimmed.

I'd like your judgment on the agent-facing descriptions in `src/operations/purchases/*.ts`. They are the only documentation an MCP client sees.

  - both receipts recorded: Farmcity read back over HTTP as printed, and Coto's 27 lines, totals, weighed lines and discounts checked;
  - a misread discount refused with difference 0.40 and nothing written;
  - a lost response retried, and the same receipt sent again from a new conversation;
  - known products linked by barcode, by store code and by text, while a 28… barcode never links;
  - a contradictory `productId` refused;
  - two signed members recording at once, each with their own email;
  - two agents sending the same receipt at once, which leaves one purchase;
  - the exact five-tool list with its hints on both MCP revisions;
  - `get_status` still answering with the schema applied.
- `tests/purchase-contracts.test.ts` covers what those examples do not reach:
  - partial and reformatted receipt identities;
  - receipt-wide adjustments and a misread subtotal;

  - chain scope, wrong check digits, ambiguous matches, branch lookup and GTIN-14 case codes;
