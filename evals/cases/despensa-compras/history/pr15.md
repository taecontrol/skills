## Description

An agent can record a receipt and read it back, but it cannot fix a line it misread, remove a purchase recorded by mistake, or find last week's purchase in a new conversation. This adds the three operations the accepted brief planned for that (`docs/design/recording-purchases.md`). They are available over MCP and `POST /api/<name>`. Closes #13.

## What changes

- **`list_purchases`** (read): summaries newest first (date, then time, with purchases that have no time last on their date, then id). Each has its chain, branch, date, time, total, `recordedBy` and revision. Optional inclusive `from`/`to`, a `chain` name (compared ignoring case, surrounding spaces and repeated spaces), `limit` 1–50 (default 20), and an opaque `cursor`, which comes back as `nextCursor`.
- **`correct_purchase`** (idempotent-write): replaces whole lines by their receipt line number, and any of the header fields (`date`, `time`, `store`, `receipt` (tax ID, point of sale and number), `subtotal`, `discounts`, `total`, receipt-wide `adjustments`). The corrected purchase must pass the same totals check as a recording. An explicit `productId` or `newProduct` wins over code matches, so a wrong link can be fixed. The answer is `corrected` or `already_applied`. It can fail with `PurchaseNotFound`, `LineNotFound`, `RevisionConflict { currentRevision }`, `TotalsMismatch`, `ProductNotFound`, `ReceiptAlreadyRecorded { otherPurchaseId }`, or `InvalidInput` (see Decisions).
- **`delete_purchase`** (destructive-write): one batch deletes the purchase's adjustments, lines and correction history, then the purchase. Products stay. An unknown or already-deleted id gets `PurchaseNotFound`, whose message says it may already have been deleted.
- `record_purchase`'s row building moved into `src/worker/purchases/write.ts` so corrections can reuse it. Its behavior and tests are unchanged.
- No migration: `purchase_corrections` already exists in production. Merging deploys, and the MCP tool list grows from five to eight.

## Decisions

- **The revision lock lives inside the batch.** The correction's `purchase_corrections` row is inserted with `revision = (select revision + 1 from purchases where id = ? and revision = ?)`. A stale revision or a missing purchase makes that NULL, the NOT NULL constraint fails, and the whole batch rolls back. The table's primary key `(purchase_id, revision)` stops two writers taking the same revision. After a failed batch the handler rereads, in this order: purchase gone → `PurchaseNotFound`; `requestId` recorded for this purchase → `already_applied`; recorded for another purchase → `InvalidInput`; revision moved → `RevisionConflict`; receipt held by another purchase → `ReceiptAlreadyRecorded`. Otherwise, or if the reread itself fails, the original database error goes out as `DatabaseFailure`. The database itself enforces the revision, the `requestId` and the receipt identity, so the checks before the batch only answer those earlier. Lines and totals are checked only before the batch, and they hold because the lock refuses the write if the purchase moved past the revision they read. Chosen products are also checked only before the batch, and nothing deletes products.
- **`linkedBy` after a correction:** it becomes `chosen` (`productId`) or `new` (`newProduct`) when the line's product changes. A corrected line that keeps its product keeps its old `linkedBy`. Sending `newProduct` always creates a product, and the tool description tells agents to send `productId` to keep one.
- **`InvalidInput` as a declared failure of `correct_purchase`:** two refusals depend on stored data, so input decoding cannot catch them. One is a `requestId` already used to correct a *different* purchase. The other is a corrected purchase whose computed totals don't fit the exact JSON money format. Both come back as `InvalidInput`, declared on this operation. The shared operation layer (ADR-0004/0006) is unchanged.
- **The cursor** is a versioned JSON string (date, time, id), decoded at the input boundary, so a malformed cursor is `InvalidInput` before any SQL runs.
- **Known limit, also added to the brief's Open risks:** products are found through the codes and text on purchase lines. After a deletion, a product that only the deleted purchase used stays in the database, but `find_products` can no longer reach it. Recording that receipt again creates new products; #8 (merging products) handles the duplicates.

## What was tested

- `vp run verify` on the final commit: format, lint and types pass; 8 test files and 47 tests pass; both builds pass.
- `tests/past-purchases.test.ts` calls the tools over MCP, alternating the two protocol revisions agents use (2026-07-28 and 2025-06-18), through the Worker's fetch handler against a real local D1 with the real migrations. It reads results back with `get_purchase` over HTTP and checks some stored rows in D1 directly. It uses the Coto and Farmcity receipts of 2026-11-01:
  - listing newest first, by chain, and by date;
  - re-linking line 21 (`GALLO`) to a new product while every other line stays the same, the corrector recorded in `purchase_corrections`, and a later receipt with that barcode linking to the corrected product;
  - a resent correction answering `already_applied`, a stale revision answering `RevisionConflict` with nothing changed, and two simultaneous corrections ending at revision 2 with one `corrected` and one `RevisionConflict`;
  - a changed amount refused with `TotalsMismatch` (subtotal off by −44.00), and two changes that cancel out accepted;
  - a corrected date, and a receipt identity that belongs to another purchase refused with `ReceiptAlreadyRecorded`;
  - `LineNotFound`, and `PurchaseNotFound` for an unknown purchase;
  - deleting a purchase: products kept, the receipt recordable again, and a second delete answering `PurchaseNotFound`.
- `tests/mcp.test.ts` checks the exact eight-tool list, with `destructiveHint` on `delete_purchase` and `idempotentHint` on `correct_purchase`.
- Not proven by a test:
  - Two parallel calls cannot be forced past the preliminary revision read together, so the simultaneous-corrections test checks the outcome, not the in-batch lock itself. The lock was reviewed in the SQL.
  - The same applies to a purchase deleted while a correction is in flight (`PurchaseNotFound` from the recovery).
  - `list_purchases` pagination (`limit`, `cursor`), the order of purchases without a time, the id tie-break, and the chain filter's case and spacing handling have no test.
  - That re-recording a deleted receipt creates new products follows from the code; the test only checks that the receipt is `recorded` again.
